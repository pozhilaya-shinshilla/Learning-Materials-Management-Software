## 1 Общие сведения

### 1.1 Введение

Настоящее техническое задание (ТЗ) распространяется на разработку веб-приложения для управления учебными материалами (далее — Веб-приложение), предназначенного для использования в ФГБОУ ВО «ВолгГТУ».

Веб-приложение представляет собой единый централизованный ресурс для хранения, структурирования, поиска и предоставления доступа к учебным материалам (лекциям, методическим указаниям, презентациям, заданиям). Область применения — цифровизация образовательного процесса, обеспечение удобного доступа студентов и преподавателей к учебным ресурсам, а также автоматизация процессов публикации и управления материалами.

### 1.2  Основание для выполнения работ

## 2 Назначение веб-приложения

Веб-приложение для управления учебными материалами должно представлять собой единый ресурс для централизованного хранения, систематизации и предоставления доступа к учебно-методическим материалам. На базе веб-приложения ФГБОУ ВО «ВолгГТУ» будет организована работа с учебными материалами.

Пользователи (преподаватели и обучающиеся) должны иметь доступ к информации об опубликованных учебных ресурсах, возможность просмотра, поиска и скачивания материалов, а также управления ими (для преподавателей) посредством веб-интерфейса.

## 3 Описание работы веб-приложения

### 3.1 Схема взаимодействия пользователей с платформой

Веб-приложение представляет собой единый ресурс для управления учебными материалами, предназначенный для автоматизации процессов публикации, хранения, поиска и предоставления доступа к учебным ресурсам. Взаимодействие с платформой строится на основе ролевой модели, включающей три категории пользователей: Студент, Преподаватель и Администратор.

Пользователи получают доступ к функциям системы после прохождения процедуры аутентификации. Администратор имеет полный доступ ко всем функциям системы: управление пользователями (создание, блокировка, удаление, изменение ролей), управление структурой дисциплин и категорий материалов, просмотр системного журнала событий.

Преподаватель после авторизации получает доступ к панели управления материалами. Преподаватель может загружать новые учебные материалы в поддерживаемых форматах (PDF, DOCX, PPTX), структурировать их по дисциплинам и темам, редактировать метаданные материалов и удалять устаревшие материалы.

Студент после входа в систему получает доступ к каталогу учебных материалов, где может осуществлять просмотр, поиск и фильтрацию материалов по различным критериям, скачивать файлы и добавлять материалы в избранное.

### 3.2 Архитектура веб-приложения

Архитектура веб-приложения строится по принципу клиент-сервер с выделением следующих компонентов:

- Клиентская часть (Frontend) — пользовательский интерфейс, реализованный с использованием современных веб-технологий и адаптированный для работы на персональных компьютерах и мобильных устройствах;

- Серверная часть (Backend) — обеспечивает обработку запросов, бизнес-логику и взаимодействие с базой данных;

- База данных — хранит информацию о пользователях, материалах и системных настройках;

- Система хранения файлов — предназначена для хранения загружаемых учебных материалов.

Компоненты системы должны быть развернуты на серверной инфраструктуре Заказчика и обеспечивать возможность масштабирования при росте нагрузки.

## 4 Требования к системе

### 4.1 Функциональные требования

Веб-приложение должно предоставлять Пользователям следующие возможности:

- идентификация, аутентификация и авторизация пользователей;

- просмотр каталога учебных материалов;

- поиск и фильтрация материалов по различным критериям;

- скачивание файлов учебных материалов;

- добавление материалов в избранное;

- загрузка новых учебных материалов (для преподавателей);

- редактирование и удаление учебных материалов (для преподавателей);

- управление пользователями и их ролями (для администратора);

- просмотр системного журнала событий (для администратора).

Для выполнения возложенных функций веб-приложение должно включать в себя следующие функциональные модули:

1.  Модуль идентификации, аутентификации и авторизации пользователей;

2.  Модуль управления учебными материалами;

3.  Модуль поиска и фильтрации;

4.  Модуль управления пользователями;

5.  Модуль хранения и управления файлами;

6.  Модуль логирования действий пользователей.

#### 4.1.1 Идентификация, аутентификация и авторизация пользователей

Процесс идентификации и аутентификации пользователей выполняется по логину и паролю. Пароль должен храниться в базе данных в зашифрованном виде с использованием алгоритмов хеширования. Восстановление пароля осуществляется через форму восстановления с отправкой ссылки на электронную почту пользователя.

Должна быть реализована ролевая модель доступа с тремя ролями:

- **Студент** — доступ к просмотру, поиску, скачиванию материалов и добавлению в избранное;

- **Преподаватель** — доступ к управлению материалами (добавление, редактирование, удаление);

- **Администратор** — полный доступ ко всем функциям системы.

#### 4.1.2 Управление учебными материалами

В системе должны быть реализованы следующие функции:

- создание материала с указанием названия, описания, дисциплины, темы и прикреплением файла;

- редактирование метаданных материала;

- удаление материала;

- просмотр списка материалов с возможностью сортировки и фильтрации;

- скачивание прикрепленных файлов.

Поддерживаемые форматы файлов: PDF, DOCX, PPTX, XLSX, JPG, PNG. Максимальный размер файла — 20 МБ.

#### 4.1.3 Поиск и фильтрация

Система должна обеспечивать:

- полнотекстовый поиск по названиям и описаниям материалов;

- фильтрацию материалов по дисциплине;

- фильтрацию по типу файла;

- фильтрацию по дате загрузки;

- сортировку результатов по дате (новые/старые), по названию (А-Я).

#### 4.1.4 Управление пользователями

Администратор должен иметь возможность:

- просматривать список всех зарегистрированных пользователей;

- изменять роли пользователей;

- блокировать и разблокировать учетные записи;

- удалять пользователей.

#### 4.1.5 Системное логирование

Система должна вести журнал действий пользователей с фиксацией следующих событий:

- вход и выход пользователей из системы;

- добавление, редактирование и удаление материалов;

- загрузка файлов;

- изменения в учетных записях пользователей.

### 4.2 Нефункциональные требования

#### 4.2.1 Требования к надежности

Веб-приложение должно сохранять работоспособность при штатных нагрузках. Должна быть реализована обработка ошибок ввода/вывода данных. В случае сбоя система не должна терять данные и должна корректно завершать текущие операции.

При возникновении следующих аварийных ситуаций система должна автоматически восстанавливать свою работоспособность:

- при сбоях в электроснабжении аппаратной части (восстановление происходит после перезапуска ОС);

- при ошибках в работе аппаратных средств (восстановление функций возлагается на ОС);

- при ошибках, связанных с программным обеспечением (восстановление работоспособности возлагается на ОС).

Должно быть обеспечено резервное копирование базы данных и файлов материалов с периодичностью, определяемой администратором системы.

#### 4.2.2 Условия эксплуатации

Устанавливаются следующие общие требования к условиям эксплуатации и техническому обслуживанию:

- Эксплуатация и техническое обслуживание средств должно осуществляться системным администратором;

## 5. Состав и содержание работ по доработке программных средств

Разработка веб-приложения для управления учебными материалами выполняется на основе типового прототипа системы управления контентом (CMS), предоставляемого Заказчиком. В рамках доработки прототипа выполняются следующие виды работ.

### 5.1. Доработка структуры базы данных

Требуется расширить типовую схему базы данных прототипа для хранения информации об учебных материалах. Необходимо добавить таблицы и поля:

таблица «Материалы»: идентификатор, название, описание, идентификатор дисциплины, идентификатор темы, имя файла, тип файла, размер файла, дата загрузки, идентификатор автора (преподавателя);

таблица «Дисциплины»: идентификатор, название дисциплины;

таблица «Избранное»: связь «пользователь — материал»;

таблица «Журнал событий»: идентификатор пользователя, тип события, дата и время, объект действия.

### 5.2. Доработка модуля управления материалами

На базе типовых CRUD-операций прототипа необходимо реализовать:

загрузку файлов с проверкой допустимых форматов (PDF, DOCX, PPTX, XLSX, JPG, PNG) и ограничением размера (не более 20 МБ);

редактирование метаданных материала без повторной загрузки файла;

удаление материала с возможностью мягкого удаления (перемещение в корзину);

отображение списка материалов с сортировкой и фильтрацией.

### 5.3. Доработка модуля поиска

Требуется реализовать полнотекстовый поиск по названию и описанию материала с учётом морфологии русского языка. Необходимо добавить фильтрацию по кафедре, дисциплине, семестру, типу файла и дате загрузки, а также сортировку результатов по дате и названию.

### 5.4. Доработка модуля аутентификации и разграничения прав

В прототипе предусмотрена базовая аутентификация. Требуется доработать её для поддержки трёх ролей: Студент, Преподаватель, Администратор. Необходимо реализовать:

разграничение доступа к функциям системы в соответствии с ролью;

восстановление пароля через электронную почту;

хранение паролей в хешированном виде (bcrypt или pbkdf2).

### 5.5. Доработка модуля логирования

Требуется дополнить прототип модулем ведения журнала действий пользователей. В журнал должны записываться:

вход и выход пользователей;

добавление, редактирование и удаление материалов;

загрузка файлов;

изменение учётных записей пользователей.

Просмотр журнала должен быть доступен администратору.

### 5.6. Доработка модуля управления пользователями

Регистрация пользователей должна осуществляться администратором.

### 5.7. Доработка пользовательского интерфейса

На основе типового интерфейса прототипа необходимо разработать:

интерфейс студента: каталог материалов, поиск, фильтрация, избранное, скачивание файлов;

интерфейс преподавателя: панель управления материалами (добавление, редактирование, удаление);

интерфейс администратора: управление пользователями (изменение ролей, блокировка, удаление), просмотр журнала событий.

Вёрстка должна быть адаптивной и корректно отображаться на экранах шириной от 320 пикселей.

### 5.8. Разработка программного интерфейса (API)

Для взаимодействия клиентской и серверной частей требуется реализовать REST API со следующими методами:

POST /api/v1/auth/login — аутентификация;

GET /api/v1/materials — получение списка материалов с фильтрацией;

POST /api/v1/materials — загрузка материала (для преподавателя);

PUT /api/v1/materials/{id} — редактирование материала;

DELETE /api/v1/materials/{id} — удаление материала;

GET /api/v1/users — управление пользователями (для администратора).

## 6. Состав и содержание работ по развертыванию

### 6.1. Требования к среде развертывания

Развертывание веб-приложения должно производиться на серверной инфраструктуре Заказчика (ФГБОУ ВО «ВолгГТУ»). Система должна быть развернута в двух экземплярах:

тестовая среда — для проведения предварительных испытаний и отладки;

промышленная среда — для опытной эксплуатации и дальнейшего использования.

Развертывание выполняется с использованием технологии контейнеризации Docker. Это обеспечивает идентичный запуск системы как на компьютере разработчика, так и на сервере Заказчика.

Минимальные системные требования к серверу:

операционная система: Linux (Ubuntu 20.04 и выше) или Windows Server с поддержкой WSL2;

установленное ПО: Docker Engine (версия 24.0 и выше), Docker Compose (v2.x);

процессор: не менее 4 ядер;

оперативная память: не менее 8 ГБ;

свободное дисковое пространство: не менее 100 ГБ;

открытые порты: 80/443 (веб-интерфейс), 5432 (база данных).

### 6.2. Архитектура контейнеризации

Система собирается и запускается в изолированном сетевом контуре через конфигурационный файл docker-compose.yml, включающий следующие сервисы:

db — сервер базы данных (PostgreSQL) с подключенным томом для сохранения данных;

backend — сервер прикладной логики (REST API), выполняющий обработку запросов и взаимодействие с базой данных;

frontend — веб-приложение интерфейсов студента, преподавателя и администратора (Nginx / SPA).

### 6.3. Порядок и сценарий запуска

Процесс ввода системы в эксплуатацию не требует установки сторонних библиотек и выполняется по стандартному сценарию:

Клонирование проекта: получение исходного кода из Git-репозитория.

Инициализация конфигурации: копирование типового файла переменных окружения cp .env.example .env (параметры по умолчанию оптимизированы для локального запуска).

Сборка и старт контейнеров: выполнение команды docker compose up --build -d.

Автоматическая инициализация: контейнеры в порядке зависимостей (depends_on) применяют миграции структуры БД и выполняют первичное наполнение демонстрационными данными (учетные записи ролей, стартовые материалы).

### 6.4. Проверка работоспособности

Успешность развертывания проверяется доступностью основных компонентов через браузер:

Пользовательский веб-интерфейс: http://localhost:3000 (или http://localhost);

Интерактивная документация API (Swagger UI): http://localhost:8000/docs;

Проверка готовности сервиса (Healthcheck): http://localhost:8000/api/v1/health.

Остановка и очистка контейнеров выполняется командой docker compose down.

## 7. Порядок контроля и приемки

### 7.1. Виды испытаний

Для проверки соответствия разработанного веб-приложения требованиям настоящего технического задания проводятся следующие виды испытаний:

предварительные испытания — проводятся на тестовой среде после завершения разработки;

опытная эксплуатация — проводится на промышленной среде в реальных условиях работы кафедры;

приемо-сдаточные испытания — проводятся по завершении опытной эксплуатации.

### 7.2. Предварительные испытания

Предварительные испытания проводятся согласно разработанной Программе и методике испытаний. Целью испытаний является проверка работоспособности основных функциональных модулей:

аутентификация и авторизация пользователей с разграничением ролей;

загрузка, редактирование и удаление учебных материалов;

поиск и фильтрация материалов;

управление пользователями (для администратора);

ведение журнала событий.

По результатам предварительных испытаний составляется протокол, в котором фиксируются выявленные замечания и сроки их устранения.

### 7.3. Опытная эксплуатация

Опытная эксплуатация проводится с целью проверки работоспособности веб-приложения в реальных условиях эксплуатации. В ходе опытной эксплуатации определяются:

количественные и качественные характеристики работы системы;

готовность персонала (преподавателей и администратора) к работе с системой;

необходимость корректировки документации.

По завершению опытной эксплуатации оформляется отчёт, в котором отражаются выявленные замечания. Все замечания должны быть устранены Исполнителем до начала приемо-сдаточных испытаний.

### 7.4. Приемо-сдаточные испытания

Приемо-сдаточные испытания проводятся на площадке Заказчика. Испытания проводятся согласно Программе и методике приемо-сдаточных испытаний, разработанной Исполнителем и согласованной с Заказчиком.

В ходе приемо-сдаточных испытаний проверяется:

полнота реализации функциональных требований (раздел 4.1);

соответствие нефункциональным требованиям (раздел 4.2);

корректность работы системы в штатных и внештатных ситуациях;

соответствие состава программной документации требованиям раздела 5.

При обнаружении несоответствий испытания прерываются с оформлением соответствующего протокола. Исполнитель устраняет выявленные несоответствия, после чего испытания повторяются.

При отсутствии замечаний и достижении всех характеристик, описанных в Программе и методике приемо-сдаточных испытаний, составляется Акт о проведении приемо-сдаточных испытаний и сдачи-приемки выполненных работ.

### 7.5. Критерии приемки

Работа считается выполненной и принятой Заказчиком при одновременном выполнении следующих условий:

все функциональные требования, перечисленные в разделе 4.1, реализованы и проверены;

система выдерживает нагрузку при одновременной работе до 100 пользователей;

время отклика системы при поиске и загрузке материалов не превышает 3 секунд;

состав переданной программной документации соответствует разделу 5 настоящего ТЗ;

подписан Акт о проведении приемо-сдаточных испытаний и сдачи-приемки выполненных работ.

### 10.3. Требования к квалификации в области веб-разработки

Исполнитель должен владеть:

языками HTML5, CSS3, JavaScript (или TypeScript);

одним из современных фреймворков для разработки веб-интерфейсов (React, Vue или аналог);

навыками адаптивной вёрстки и обеспечения кросс-браузерной совместимости;

опытом работы с асинхронными запросами к API.

### 10.4. Требования к квалификации в области развертывания

Исполнитель должен владеть:

системой контроля версий Git;

технологией контейнеризации Docker и написанием сценариев docker-compose.yml;

навыками настройки веб-сервера (Nginx или аналог);

навыками резервного копирования и восстановления баз данных.

### 10.5. Требования к оформлению документации

Исполнитель должен обладать навыками оформления технической документации в соответствии с требованиями ГОСТ 19.xxx и ГОСТ 34.xxx, а также требованиями к оформлению учебных проектов ВолгГТУ.

### 10.6. Состав команды

Для выполнения работ по настоящему ТЗ рекомендуется следующий состав проектной группы:

Backend-разработчик — реализация серверной логики, API, работы с базой данных;

Frontend-разработчик — реализация пользовательских интерфейсов для трёх ролей;

DevOps-специалист — настройка контейнеризации, развертывание, резервное копирование;

Аналитик / технический писатель — подготовка документации, координация требований.

Допускается совмещение ролей одним участником при условии выполнения всех требований к квалификации, перечисленных в пп. 10.2–10.5.
