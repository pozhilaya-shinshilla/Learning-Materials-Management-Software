# Архитектура

## Слои

```
api/        → зависит от services/ (через ApplicationContext) и dtos/; HTTP, роутеры, Depends
cli/        → зависит от services/
dtos/       → Pydantic-схемы запросов и ответов API (зависят только от domain/)
runtime.py  → старт «по-настоящему»: настройки, проверка БД, сборка (общий для cli/ и api/)
services/   → зависит от repositories/interfaces.py и domain/
repositories/interfaces.py   → интерфейсы хранилищ для сервисов (ABC), не зависят ни от чего
repositories/abstract.py   → AbstractRepository: контракт add/get_by_id/get_all/update/delete
repositories/sqlalchemy.py → SQLAlchemyRepository и репозитории ORM-моделей; Session снаружи, без commit
repositories/domain_adapters.py → интерфейсы сервисов поверх ORM-репозиториев + мапперы
database/   → модели, мапперы, сессии, транзакции; доменный слой о нём не знает
domain/     → сущности, enum'ы, исключения — не зависят ни от чего
security/   → интерфейс хеширования паролей + PBKDF2-реализация
notifications/ → интерфейс отправки писем + консольная имитация
```

Зависимость всегда направлена внутрь, к `domain/`: `cli` не знает о `repositories`,
`services` не знают, что хранилище — это PostgreSQL, а не что-то другое
(Dependency Inversion Principle). `bootstrap.py` — единственное место, где происходит
сборка (Composition Root): создаются конкретные реализации репозиториев и хешера
паролей и передаются в сервисы через конструктор.

## Домен: enum'ы, исключения, валидация

- `enums.py` — у каждого значения есть машинное имя (`value`) и русская подпись (`label`),
  которую показывает интерфейс.
- `exceptions.py` — иерархия от `DomainError`, сгруппированная по смыслу: аутентификация и права,
  сущности (не найдена / дубликат), проверка данных (`ValidationError` и его наследники для файлов).
  Интерфейсу достаточно ловить `DomainError`.
- `validation.py` — чистые функции разбора и проверки ввода (`parse_positive_int`, `parse_yes_no`,
  `parse_role`, `parse_file_type`, `require_text`, `OptionalParser(...)`). Они бросают `ValidationError`
  с понятным текстом; CLI по этому тексту переспрашивает поле на месте.

## Поиск и восстановление пароля

- Поиск полнотекстовый и целиком в БД: `SearchService` переводит пользовательский фильтр в
  `MaterialSearchQuery` (`domain/search.py`), а `MaterialRepository.search` выполняет один SQL-запрос:
  условия, `to_tsvector('russian', название || описание) @@ to_tsquery(...)` по GIN-индексу
  `ix_materials_search_vector` и `ORDER BY`. Морфологию (основы слов, «ё», стоп-слова, английский)
  выполняет PostgreSQL. Даты фильтра переводятся в границы суток в часовом поясе приложения
  (`APP_TIMEZONE`). Сортировку выбирает стратегия (`repositories/sorting.py`): она возвращает
  SQL-выражение, поэтому весь каталог в память не загружается. Индекс по выражению создан в миграции
  вручную: Alembic такие индексы не сравнивает, поэтому в `include_in_autogenerate` он помечен как
  управляемый вручную, а тесты проверяют, что индекс существует и что запрос им пользуется.
- `AuthService` зависит от абстракции `EmailSender`: коды восстановления хранятся как SHA-256,
  одноразовые, с ограниченным сроком; новый запрос аннулирует прежний код.

## Роли и разграничение доступа

Проверка прав не размазана по CLI, а инкапсулирована в сервисах: каждый метод
сервиса, требующий определённой роли, сам проверяет `requesting_user.role`
и выбрасывает `AuthorizationError`, если доступ запрещён. CLI лишь перехватывает
`DomainError` и печатает сообщение — он не принимает решений о правах.

## Почему принципы SOLID не нарушены

- **SRP** — `AuthService` только про вход/выход и восстановление пароля,
  `UserManagementService` — только про управление учётными записями,
  `MaterialService` — только про материалы, `SearchService` — только про
  поиск/фильтрацию/сортировку, `FavoriteService` — только про избранное,
  `EventLogService` — только про журнал событий, `CatalogService` — только
  про дисциплины и темы.
  На уровне CLI то же разделение: `ConsoleIO`, `MenuRenderer`, `Presenter`, `Picker`,
  `AuthController` и по контроллеру на роль, а `CliApplication` только связывает их (см. «Устройство CLI»).
- **OCP** — новый тип хранилища добавляется новым классом, реализующим
  соответствующий `*Repository`, без изменения кода сервисов.
- **LSP** — любая реализация `UserRepository`/`MaterialRepository`/... может
  быть подставлена вместо SQL-реализации без изменения поведения, ожидаемого
  сервисами (в контрактах интерфейсов нет специфики конкретной СУБД).
- **ISP** — репозитории разделены по сущностям, а не собраны в один
  «толстый» интерфейс `Repository`, к которому сервисам приходилось бы
  реализовывать лишние методы.
- **DIP** — сервисы принимают абстракции (`UserRepository`, `PasswordHasher`
  и т.д.) через конструктор; конкретные реализации подставляются в
  `bootstrap.py`.

## Устройство CLI

`CliApplication` (`cli/app.py`) только ведёт цикл: показывает экран входа, выбирает контроллер
по роли пользователя и запускает выбранный пункт меню. Остальное разложено по классам
с одной причиной для изменения:

- `ConsoleIO` — ввод с повторным запросом при ошибке, подтверждения, очистка экрана, паузы;
- `MenuRenderer` — отрисовка меню и чтение номера пункта;
- `Presenter` — форматирование и печать материалов, пользователей и журнала событий;
- `Picker` — выбор дисциплины, темы, материала или пользователя из показанного списка;
- `AuthController` — вход, выход, восстановление пароля;
- `StudentController` → `TeacherController` → `AdminController` — сценарии ролей; каждая
  следующая роль наследует пункты меню предыдущей и добавляет свои (`menu_items()`).

Контроллеры получают `ApplicationContext` и берут из него только нужные сервисы;
парсеры ввода — методы классов или `OptionalParser`, вложенных функций нет.

## REST API (FastAPI)

```
HTTP-запрос → роутер (api/routers/*.py) → сервис (services/*.py) → репозиторий → PostgreSQL
              ↑ Pydantic-запрос (dtos/requests.py)          ↓
              ← Pydantic-ответ (dtos/responses.py) ← доменный объект
```

- `api/app.py` — фабрика `create_app()`: подключает роутеры и обработчик ошибок, при старте собирает
  сервисы (`runtime.build_runtime_context`). В тестах `create_app(context)` принимает готовый контекст.
- `api/dependencies.py` — зависимости `Depends`: `ContextDep` (сервисы), `CurrentUser` (пользователь
  по токену), `AdminUser` (только администратор). Роутеры не создают сервисы сами.
- `api/errors.py` — единственное место, где ошибки предметной области (`DomainError`) получают HTTP-статус
  (401, 403, 404, 409, 413, 415, 422). Тело ошибки всегда `{"detail": "...", "code": "ИмяКласса"}`.
- Роутеры тонкие: разобрать запрос, вызвать сервис, вернуть DTO. Каждый маршрут объявляет `response_model`
  (кроме `204` и скачивания файла), поэтому в ответ попадают только поля схемы.
- Сервисы синхронные, поэтому маршруты объявлены как `def`: FastAPI выполняет их в пуле потоков, а
  `TransactionManager` держит сессию и состояние транзакции отдельно для каждого потока.
- Вход по токену: `SessionService` (Facade) выдаёт токен, в БД лежит только его SHA-256 (`auth_tokens`).
  На каждый запрос пользователь читается из БД заново, поэтому смена роли и блокировка действуют сразу.

## Точка входа и запуск

`src/main.py` — единственная точка входа (`serve` по умолчанию, `cli`, `migrate`).

```
main.py → check_configuration()   настройки проверены до запуска (понятная ошибка вместо трассировки)
        → prepare_database()      wait_for_database (до DB_WAIT_SECONDS) → upgrade_to_head (AUTO_MIGRATE)
        → uvicorn.run(create_app())  / CliApplication(...).run()
```

- `upgrade_to_head` держит консультативную блокировку PostgreSQL (`pg_advisory_lock`): если две копии
  приложения стартуют одновременно, схему обновляет одна, вторая ждёт и видит, что всё применено.
- Сервер и консоль собираются одной функцией `build_transactional_context`, поэтому правила транзакций,
  блокировок и отложенных писем у них одинаковые.
- `Dockerfile` собирает образ (зависимости по `uv.lock`, не root, `HEALTHCHECK` на `/api/health`),
  `docker-compose.yaml` поднимает `db` и `app` (после готовности БД), загрузки лежат в томе.

## Роли в API

Права проверяют сервисы (единый источник правил для консоли и API). `AdminUser` в роутерах добавляет
ранний отказ `403` для методов администратора. Студент: просмотр, поиск, скачивание, избранное.
Преподаватель: плюс материалы, дисциплины и темы. Администратор: всё, включая пользователей и журнал.

## Хранение в PostgreSQL

- Репозитории PostgreSQL устроены как в методичке: `AbstractRepository` (`abstract.py`) →
  общий `SQLAlchemyRepository` с атрибутом `model` → конкретные `UserRepository`,
  `MaterialRepository` и др. (`sqlalchemy.py`), работающие с ORM-моделями. Сервисам нужны
  интерфейсы предметной области (`interfaces.py`), поэтому между ними стоит слой адаптеров
  `domain_adapters.py`.
- `domain/models.py` — чистые dataclass-ы. `database/models.py` — ORM-модели таблиц. Между ними
  стоят классы-мапперы (`database/mappers.py`, Data Mapper): репозиторий принимает и отдаёт
  доменные объекты, поэтому сервисы и CLI не видят ни сессий, ни ленивых связей.
- Репозиторий получает `Session` в конструктор, делает `flush()`, но не `commit()`. Транзакцией
  владеет `TransactionManager` (`database/transaction.py`): сессия создаётся на операцию, а
  каждый публичный метод сервиса выполняется в одной транзакции через `TransactionalService`
  (Proxy). В терминах Фаулера `Session` — это Unit of Work, а `TransactionManager` — граница, которая
  решает его исход (см. `design-patterns.md`). Корень сборки (`bootstrap.py`) подставляет прокси только для БД.
- Фиксация: без ошибок и при `DomainError` (нарушение бизнес-правила, например неверный пароль
  при входе: событие журнала должно сохраниться) — `commit`; при любой другой ошибке — `rollback`.
- Удаление автора: `materials.author_id` и `events.user_id` становятся `NULL` (`ON DELETE SET NULL`),
  закладки удаляются каскадом.
- Схему создаёт и меняет только Alembic; приложение при старте проверяет, что миграции применены.
- **Состояние приложения лежит в БД, а не в памяти процесса.** Коды восстановления пароля
  (`password_reset_tokens`, хранится только SHA-256 кода и срок жизни), счётчик неудачных входов
  (`failed_logins`) и снимки правок материалов для отмены (`material_revisions`, не более 20 на
  материал) доступны всем процессам и переживают перезапуск. Это то, чего требует работа в
  нескольких воркерах: состояние в памяти одного процесса другие процессы не видят.
- Кеша материалов в памяти процесса нет: в нескольких воркерах он устаревал бы независимо в каждом.
  При необходимости кеш выносится в общее хранилище (например, Redis) или заменяется HTTP-кешированием.
- Состояние, которое остаётся в памяти процесса, живёт одно обращение: сессия SQLAlchemy на операцию
  и `list_all()` без кеширования.

### Одновременная работа нескольких пользователей

Уровень изоляции — `READ COMMITTED` (по умолчанию в PostgreSQL): проверка «такого ещё нет» и
последующая запись не атомарны, потому что между ними другая транзакция успевает зафиксировать
своё. Поэтому для каждого места, где это важно, выбран явный механизм:

| Ситуация | Механизм |
|---|---|
| Двое создают одинаковый логин, email, дисциплину, тему, закладку | Последнее слово за уникальным индексом БД. `domain_adapters._translate_conflicts` пишет в `SAVEPOINT` и превращает `IntegrityError` в `Duplicate*Error`: пользователь видит обычное сообщение, транзакция остаётся рабочей |
| Код восстановления использовали дважды | `consume`: проверка срока и удаление — один `DELETE ... RETURNING`; код получает только первый |
| Два запроса кода для одного пользователя | `UserRepository.lock`: строка пользователя блокируется (`FOR NO KEY UPDATE`), второй запрос отзывает код первого |
| Двое правят, отменяют правку или удаляют один материал | `MaterialRepository.get_by_id_for_update`: операции выстраиваются в очередь, снимок для отмены берётся с настоящего прежнего состояния, правка удалённого материала даёт `MaterialNotFoundError` |
| Роль пользователя изменили во время его сеанса | `AuthService.ensure_session_active` сверяет роль со свежей записью и завершает сеанс (`RoleChangedError`); права определяет объект `User`, полученный при входе, поэтому без этого понижение работало бы только после выхода |
| Пользователя или материал удалили посреди чужой операции | Нарушение внешнего ключа превращается в `AccountDeletedError` / `MaterialNotFoundError` |
| Два неудачных входа одного логина подряд, оба доходят до порога | `FailedLoginRepository.register` берёт `pg_advisory_xact_lock` на логин: вторая попытка ждёт первую и считает с учётом её строки, письмо уходит одно. Блокировка не привязана к строке, потому что у несуществующих логинов строк в `users` нет |
| Удаление пользователя и правка, отмена или удаление его материала | Единый порядок блокировок, см. ниже |

Ошибки, вызванные гонкой, помечены `rolls_back_transaction = True`: `TransactionManager` откатывает
операцию целиком, а не фиксирует её частично (обычный `DomainError` по-прежнему фиксируется).

#### Порядок блокировок

Взаимную блокировку (deadlock) даёт не сама блокировка, а противоположный порядок: одна транзакция
держит строку А и ждёт Б, другая держит Б и ждёт А, и PostgreSQL отменяет одну из них. В проекте
был такой случай. `DELETE FROM users` берёт строку пользователя, а затем обнуляет `author_id` у
его материалов (`ON DELETE SET NULL`), то есть берёт строки материалов. Правка материала шла
наоборот: брала материал (`FOR NO KEY UPDATE`), а затем записывала событие журнала, и внешний ключ
`events.user_id` требовал строку пользователя (`FOR KEY SHARE`). Теперь везде один порядок:

1. строки пользователей, по возрастанию `id`;
2. строка материала.

Это правило выполняют `MaterialRepository.get_by_id_for_update(..., acting_user_id=...)` (блокирует
действующего пользователя и автора, затем материал) и `UserRepository.lock_many`
(`ORDER BY id ... FOR KEY SHARE` для обычных операций, `FOR UPDATE` для удаления). Та же причина
стояла за вторым случаем: два администратора удаляют друг друга. Каждый брал строку жертвы, а
потом писал событие со ссылкой на свою. `UserManagementService.delete_user` теперь сначала
блокирует обе строки по возрастанию `id`; проигравший получает `AccountDeletedError`.

Если пользователя удалили, пока его сеанс ещё открыт, правка, отмена и удаление материала
завершаются `AccountDeletedError` (сеанс закрывается), а не сообщением «материал чужой», как было,
когда у материала уже был обнулён автор.

#### Файлы и письма

Письмо нельзя отозвать, а файл на диске не откатывается вместе с БД, поэтому внешние действия
привязаны к исходу транзакции через `TransactionHooks` (`services/transaction_hooks.py`,
реализация — `TransactionManager`):

| Действие | Когда выполняется |
|---|---|
| Письмо с кодом восстановления, письмо о неудачных входах | `on_commit`: после фиксации. Откат ничего не отправит, соединение с БД к этому времени возвращено в пул и не ждёт SMTP с повторами |
| Удаление файла материала | `on_commit`: если фиксация не пройдёт, строка останется и файл тоже |
| Копирование файла при создании материала | сразу (путь и размер нужны для строки), но с `on_rollback`: при откате копия удаляется |

`transaction_scope` и `transaction_hooks` в `build_application_context` задаются только вместе:
без хуков письмо ушло бы из открытой транзакции. Ошибка действия «после фиксации» не отменяет
операцию (она уже зафиксирована) и пишется в лог: например, не отправленное письмо с кодом
пользователь запросит заново.

Известные ограничения: если процесс остановится между фиксацией и отправкой письма, письмо
потеряется, а если он остановится после копирования файла, но до фиксации, останется файл без
строки (он лишь занимает место). Гарантированную доставку даёт «ящик исходящих» (outbox): письмо записывается в таблицу в
той же транзакции, а отдельный процесс его отправляет. Для учебного приложения с консольной
почтой это избыточно.
