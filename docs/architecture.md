# Архитектура (этап 1)

## Слои

```
cli/        → зависит от services/
services/   → зависит от repositories/interfaces.py и domain/
repositories/interfaces.py → абстракции (ABC), не зависят ни от чего
repositories/in_memory.py  → одна из возможных реализаций интерфейсов
domain/     → сущности, enum'ы, исключения — не зависят ни от чего
security/   → интерфейс хеширования паролей + PBKDF2-реализация
notifications/ → интерфейс отправки писем + консольная имитация
```

Зависимость всегда направлена внутрь, к `domain/`: `cli` не знает о `repositories`,
`services` не знают, что хранилище — это словарь в памяти, а не PostgreSQL
(Dependency Inversion Principle). `bootstrap.py` — единственное место, где происходит
сборка (Composition Root): создаются конкретные реализации репозиториев и хешера
паролей и передаются в сервисы через конструктор.

## Домен: enum'ы, исключения, валидация

- `enums.py` — у каждого значения есть машинное имя (`value`) и русская подпись (`label`),
  которую показывает интерфейс.
- `exceptions.py` — иерархия от `DomainError`, сгруппированная по смыслу: аутентификация и права,
  сущности (не найдена / дубликат), проверка данных (`ValidationError` и его наследники для файлов).
  Интерфейсу достаточно ловить `DomainError`.
- `validation.py` — чистые функции разбора и проверки ввода (`parse_positive_int`, `parse_yes_no`,
  `parse_role`, `parse_file_type`, `require_text`, `OptionalParser(...)`). Они бросают `ValidationError`
  с понятным текстом; CLI по этому тексту переспрашивает поле на месте.

## Поиск и восстановление пароля

- `services/morphology.py` — токенизация и нормализация слов (русский и английский) через стеммеры Snowball из библиотеки NLTK.
  `SearchService` использует их, поэтому поиск не зависит от хранилища и работает одинаково
  для in-memory и будущей PostgreSQL-реализации (при необходимости заменяется полнотекстовым
  поиском СУБД).
- `AuthService` зависит от абстракции `EmailSender`: коды восстановления хранятся как SHA-256,
  одноразовые, с ограниченным сроком; новый запрос аннулирует прежний код.

## Роли и разграничение доступа

Проверка прав не размазана по CLI, а инкапсулирована в сервисах: каждый метод
сервиса, требующий определённой роли, сам проверяет `requesting_user.role`
и выбрасывает `AuthorizationError`, если доступ запрещён. CLI лишь перехватывает
`DomainError` и печатает сообщение — он не принимает решений о правах.

## Почему принципы SOLID не нарушены

- **SRP** — `AuthService` только про вход/выход и восстановление пароля,
  `UserManagementService` — только про управление учётными записями,
  `MaterialService` — только про материалы, `SearchService` — только про
  поиск/фильтрацию/сортировку, `FavoriteService` — только про избранное,
  `EventLogService` — только про журнал событий, `CatalogService` — только
  про дисциплины и темы.
  На уровне CLI то же разделение: `ConsoleIO`, `MenuRenderer`, `Presenter`, `Picker`,
  `AuthController` и по контроллеру на роль, а `CliApplication` только связывает их (см. «Устройство CLI»).
- **OCP** — новый тип хранилища добавляется новым классом, реализующим
  соответствующий `*Repository`, без изменения кода сервисов.
- **LSP** — любая реализация `UserRepository`/`MaterialRepository`/... может
  быть подставлена вместо `InMemory*` без изменения поведения, ожидаемого
  сервисами (в контрактах интерфейсов нет специфики in-memory реализации).
- **ISP** — репозитории разделены по сущностям, а не собраны в один
  «толстый» интерфейс `Repository`, к которому сервисам приходилось бы
  реализовывать лишние методы.
- **DIP** — сервисы принимают абстракции (`UserRepository`, `PasswordHasher`
  и т.д.) через конструктор; конкретные реализации подставляются в
  `bootstrap.py`.

## Устройство CLI

`CliApplication` (`cli/app.py`) только ведёт цикл: показывает экран входа, выбирает контроллер
по роли пользователя и запускает выбранный пункт меню. Остальное разложено по классам
с одной причиной для изменения:

- `ConsoleIO` — ввод с повторным запросом при ошибке, подтверждения, очистка экрана, паузы;
- `MenuRenderer` — отрисовка меню и чтение номера пункта;
- `Presenter` — форматирование и печать материалов, пользователей и журнала событий;
- `Picker` — выбор дисциплины, темы, материала или пользователя из показанного списка;
- `AuthController` — вход, выход, восстановление пароля;
- `StudentController` → `TeacherController` → `AdminController` — сценарии ролей; каждая
  следующая роль наследует пункты меню предыдущей и добавляет свои (`menu_items()`).

Контроллеры получают `ApplicationContext` и берут из него только нужные сервисы;
парсеры ввода — методы классов или `OptionalParser`, вложенных функций нет.

## Известное отступление от «идеального» SOLID

`ApplicationContext` остаётся «толстым» набором всех сервисов, но зависимость от него есть только
у контроллеров и корня сборки. При переходе на FastAPI (следующий этап) контроллеры
заменятся отдельными роутерами (`auth.py`, `materials.py`, `users.py`, ...), каждый из которых
будет зависеть только от нужных ему сервисов.
