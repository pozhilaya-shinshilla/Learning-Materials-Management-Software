# Архитектура (этап 1)

## Слои

```
cli/        → зависит от services/
services/   → зависит от repositories/interfaces.py и domain/
repositories/interfaces.py → абстракции (ABC), не зависят ни от чего
repositories/in_memory.py  → одна из возможных реализаций интерфейсов
domain/     → сущности, enum'ы, исключения — не зависят ни от чего
security/   → интерфейс хеширования паролей + PBKDF2-реализация
```

Зависимость всегда направлена внутрь, к `domain/`: `cli` не знает о `repositories`,
`services` не знают, что хранилище — это словарь в памяти, а не PostgreSQL
(Dependency Inversion Principle). `bootstrap.py` — единственное место, где происходит
сборка (Composition Root): создаются конкретные реализации репозиториев и хешера
паролей и передаются в сервисы через конструктор.

## Роли и разграничение доступа

Проверка прав не размазана по CLI, а инкапсулирована в сервисах: каждый метод
сервиса, требующий определённой роли, сам проверяет `requesting_user.role`
и выбрасывает `AuthorizationError`, если доступ запрещён. CLI лишь перехватывает
`DomainError` и печатает сообщение — он не принимает решений о правах.

## Почему принципы SOLID не нарушены

- **SRP** — `AuthService` только про вход/выход и восстановление пароля,
  `UserManagementService` — только про управление учётными записями,
  `MaterialService` — только про материалы, `SearchService` — только про
  поиск/фильтрацию/сортировку, `FavoriteService` — только про избранное,
  `EventLogService` — только про журнал событий, `CatalogService` — только
  про дисциплины и темы.
- **OCP** — новый тип хранилища добавляется новым классом, реализующим
  соответствующий `*Repository`, без изменения кода сервисов.
- **LSP** — любая реализация `UserRepository`/`MaterialRepository`/... может
  быть подставлена вместо `InMemory*` без изменения поведения, ожидаемого
  сервисами (в контрактах интерфейсов нет специфики in-memory реализации).
- **ISP** — репозитории разделены по сущностям, а не собраны в один
  «толстый» интерфейс `Repository`, к которому сервисам приходилось бы
  реализовывать лишние методы.
- **DIP** — сервисы принимают абстракции (`UserRepository`, `PasswordHasher`
  и т.д.) через конструктор; конкретные реализации подставляются в
  `bootstrap.py`.

## Известное отступление от «идеального» SOLID

`CliApplication` знает сразу обо всех сервисах (`AuthService`,
`UserManagementService`, `MaterialService`, `SearchService`,
`FavoriteService`, `EventLogService`, `CatalogService`). Формально это можно
расценить как нарушение ISP на уровне CLI-класса. Отступление осознанное:
CLI — это единственная точка входа пользователя на данном этапе (нет
отдельных контроллеров под каждую роль), и его роль — маршрутизация ввода
к нужному сервису, а не бизнес-логика. При переходе на FastAPI (следующий
этап) это разделится на отдельные роутеры (`auth.py`, `materials.py`,
`users.py`, ...), каждый из которых будет зависеть только от нужных ему
сервисов.
